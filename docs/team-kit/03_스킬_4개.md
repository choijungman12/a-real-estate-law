## ① team-inbox — 직원: 일 하나 맡아서 끝까지
````markdown
---
name: team-inbox
description: 직원 대화에서 일을 시작할 때. 노션 작업 DB에서 '다음' 레코드 하나를 맡아(선점) 지시를 합격표로 바꾸고 멈추지 않고 끝까지 만든 뒤 team-done으로 마치고, 같은 담당의 다음 일을 이어 맡는다. 할 일이 없으면 '할 일 없음' 한 줄.
---

# team-inbox — 맡기 → 합격표 → 끝까지 작업 → team-done → 다음 일

대화끼리는 직접 말하지 않는다. 우편함은 노션 작업 DB(`{{작업DB_ID}}`) 하나다. 노션 커넥터로 읽고 쓴다.

## 절차
1. **맡을 일 고르기.** 이 대화가 이미 맡은 담당이 있으면 그 담당만. 없으면 `상태 = 다음`이고 `담당 ≠ 총괄`인 레코드 중 마감일이 가장 빠른 것(같으면 최근 수정). `/team-inbox 프론트`처럼 담당을 붙이면 그 담당만. 후보가 0이면 대화창에 `할 일 없음`만 쓰고 끝.
   - `상태 = 진행 중`이고 메모가 `교체 대기 ·`로 시작하는 레코드가 있으면 그것이 먼저다(앞 대화가 남긴 일 → 「이어받기」).
2. **선점.** 바로 `상태 = 진행 중`, 메모 맨 앞에 `착수 M/D HH:MM ·`. 다시 읽어서 다른 착수 표시가 먼저 있으면 놓고 1번으로.
3. **이 대화의 담당 = 레코드의 `담당`.** 이후 그 역할로 판단한다.
4. **규칙 읽기.** 허브의 「규칙」 페이지(공통) + 저장소 작업이면 저장소 `CLAUDE.md`. 같은 대화 두 번째 일부터는 다시 읽지 않는다.
5. **지시 읽기.** `## 지시`에서 가장 최근 블록만. 옛 이력 전체를 다시 읽지 않는다.
6. **합격표 만들기.** 지시를 표로: `항목 · 합격 기준(숫자/눈으로 확인할 것) · 확인 방법 · 쓸 도구`. 형용사(「고급스럽게」)는 숫자 · 고유명사로 바꿔 적는다. 이름만 있고 정의가 없는 것은 내 가안으로 정의해 표에 넣는다.
7. 합격표를 `## 결과` 아래 「시작 계획 (M/D)」로 적는다. 대화창에는 쓰지 않는다.
8. **멈추지 말고 끝까지 만든다.** 승인을 기다리지 않는다. 만들고 → 실행 · 측정 · 캡처로 확인 → 실패하면 고친다. 앞 일이 없어도 할 수 있는 부분은 임시값으로 먼저 하고 나중에 바꾼다.
   - 코드면: 지정 브랜치에서 작업 → 테스트 · 빌드 통과 → PR(본문에 `Closes #이슈`) → 레코드에 PR 링크.
9. 작업 단위가 끝날 때마다 `## 결과`에 진행 기록을 짧게 남긴다(대화가 요약 · 압축돼도 레코드만 보고 이어갈 수 있게).
10. 끝나면 **team-done**. 같은 담당의 `다음` 레코드가 있으면 `작업 끝 → 이어서: <이름>`을 쓰고 2번부터 다시.

## 멈춰도 되는 경우는 이것뿐
- **결정 필요(STOP)**: 돈이 드는 것(결제 · 유료 플랜 · 크레딧 한도 초과) · 외부로 보내는 것(메일 · 메시지 · 공개 게시) · 데이터 삭제 · 운영자 명시값과 충돌 · 비밀값이 필요한 것. → `## 질문`에 선택지와 가안, `상태 = 대기`, 대화창 `작업 멈춤 — 판단 필요`.
- **도구 · PC가 막힘** → 막힌 곳과 필요한 조치를 적고 `작업 멈춤 — <막힌 것>`.
- 그 밖의 사소한 선택은 묻지 않고 가안으로 정해 결과에 적는다.

## 이어받기 (교체 대기 레코드)
메모를 `이어받음 M/D HH:MM ·`로 바꿔 선점 → `## 결과`의 가장 최근 `### 재개 메모`만 읽고 「다음 할 일」부터 이어간다. 끝난 것을 다시 만들지 않는다.

## 대화창 규칙
진행 설명 · 요약을 쓰지 않는다. 마지막 한 줄만: `작업 끝` / `작업 끝 → 이어서: <이름>` / `작업 끝 (다음 없음)` / `작업 멈춤 — …` / `할 일 없음`.
````

## ② team-done — 직원: 결과 기록하고 마치기
````markdown
---
name: team-done
description: 직원이 맡은 일을 끝냈을 때. 결과를 작업 DB 레코드에 증빙과 함께 기록하고, 상태 · 메모를 갱신하고, 임시 파일을 정리한 뒤 '작업 끝'만 남기고 같은 담당의 다음 레코드를 이어 맡는다.
---

# team-done — 결과 기록 → 상태 갱신 → 정리 → 다음 일

1. **`## 결과`에 적는다** (이 순서, 짧게):
   - 합격표 각 항목: `O / △ / X` + 실제 측정값(숫자) + 확인 방법.
   - 산출물: 파일 경로 · PR 링크 · 배포 미리보기 주소 · 캡처 몇 장.
   - 바뀐 것 / 안 바뀐 것(지시 밖은 손대지 않았음을 확인).
   - 기본값으로 정한 것(질문 대신 가안으로 정한 것들) — 번호 붙여 한 줄씩.
   - 남은 것 · 다음 제안(있으면). 판단 요청은 `## 질문`으로.
2. **기록 점검 5문항** — 하나라도 아니면 고쳐 쓴다.
   - 결과만 읽고 다른 사람이 확인할 수 있나? (경로 · 링크 · 숫자)
   - 합격표 항목이 빠짐없이 있나?
   - X · △ 는 이유와 다음 조치가 있나?
   - 대화에만 있고 레코드에 없는 내용이 0인가?
   - 비밀값(토큰 · 비밀번호 · 키)이 들어가지 않았나?
3. **상태 · 메모**: `상태 = 완료`, 메모 = `완료 M/D · <결과 한 줄> · PR #n`. STOP으로 멈춘 경우는 `대기`.
4. **정리**: 이 일로 만든 임시 파일 · 중간본을 휴지통으로(영구 삭제 X). 저장소에 넣을 것만 남긴다.
5. **다음 일**: 같은 담당의 `다음` 레코드가 있으면 `작업 끝 → 이어서: <이름>` 후 team-inbox 2번부터. 없으면 `작업 끝 (다음 없음)`.
````

## ③ team-status — 누구나: 지금 현황 한 장
````markdown
---
name: team-status
description: 운영자나 총괄이 '진행상황'을 물을 때. 작업 DB의 열린 레코드와 GitHub PR · 브랜치 활동을 모아 담당별 한 장 표로 보여 주고, 멈춘 것 같은 일을 짚는다.
---

# team-status — 현황 한 장

1. 작업 DB에서 `상태 ≠ 완료` 레코드 전부 + 최근 24시간 안에 `완료`된 레코드를 읽는다(이름 · 담당 · 상태 · 메모 · 마지막 수정).
2. 코드 저장소가 있으면 `gh pr list --state all --limit 8` 과 작업 브랜치의 마지막 커밋 시각을 본다.
3. 표로 보여 준다: `담당 · 일 · 상태 · 마지막 움직임 · 다음`.
4. **멈춤 의심**: `진행 중`인데 레코드 수정도 커밋도 3시간 넘게 없으면 「멈춘 것 같음」으로 표시하고, 그 담당에게 보낼 깨우기 한 줄을 붙인다(예: `노션 작업 DB에서 [프론트] 진행 중 레코드를 이어서 진행해라`).
5. 마감일이 있으면 남은 시간과 「맞출 수 있나」를 한 줄로.
````

## ④ team-chief — 총괄: 새 대화에서 총괄 이어받기
````markdown
---
name: team-chief
description: 새 대화를 총괄로 시작하거나 앞 총괄 대화를 이어받을 때. 허브의 '총괄 재개 메모'와 규칙, 작업 DB를 읽고 바로 판정 · 지시를 이어간다.
---

# team-chief — 총괄 이어받기

1. 허브 페이지의 「총괄 재개 메모」(없으면 새로 만든다), 「규칙」, 작업 DB 「열린 작업」 보기를 읽는다. 내 메모(기억)가 있으면 그것도.
2. `완료`인데 총괄 판정이 아직 없는 레코드부터 검수한다(`08_총괄_운영루틴`의 검수 방식).
3. 운영자에게 한 장 현황(team-status 형식) + 「지금 제가 할 것」 3줄을 보고하고 바로 진행한다.
4. 대화가 길어져 교체할 때(운영자가 말할 때만): 「총괄 재개 메모」에 지금 판단 중인 것 · 기다리는 것 · 다음 할 것 · 운영자에게 받은 결정을 적고 끝낸다.
````
